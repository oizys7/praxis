# 路线备注：本轮不做的能力，以及为什么

本文件记录**刻意推迟**的能力及其判断依据，避免以后重新争论一遍。
当前已落地的是「地板」层（资源可核查、知识点覆盖、版本事实注入），
见 `agent-service/app/{resource_check,version_check,search}.py`。

## 1. RAG 知识库 → 独立项目

**结论：不在本项目做。** 本项目是学习计划的生成器，不是知识库维护者。

理由：

- **覆盖度永远追不上**。爬完 Rust 文档，用户要学 Scala；学习目标是无方向的。
- **时效性是负资产**。技术内容过期极快，自建全网库会变成「过时知识的放大器」，
  比不做更危险。外部搜索至少带日期与权威排序。
- **维护是永续成本**。爬虫失效、去重、清洗、embedding 重算，单人无法维持。

什么情况下值得做（新项目立项条件）：

- 只收**稳定语料**：官方文档、经典书、RFC、语言规范、官方 handbook。
  体量小、变化慢、质量确定——这叫「种子库」，不是「爬全网」。
- 有明确的**封闭边界**（企业内部文档、某个产品的官方手册）。
- 有**高频重复查询**（同一领域被问上千次），缓存才摊得薄。

**不要**引入「学习算法」：冷启动阶段没有用户行为数据可学，那是幻想。
规则打分（域名层级、时效、可达性）有效，但那不叫学习算法。

## 2. 向量检索 → 等一个具体理由

**结论：现在不做，但已选定技术路径。**

技术选型（已核实可用）：

| 用途 | 库 | 说明 |
|---|---|---|
| 向量存储 | `pgvector-rust` 0.4.2 | **支持 SQLx**，直接落在现有 Postgres，不引入新服务 |
| 本地嵌入 | `fastembed` 7.2 | 本地 ONNX，同步、不依赖 tokio，无需 API key |
| 全文检索 | `tantivy` 0.27 | BM25，技术内容的精确匹配强于向量 |

**引入的唯一正当理由：跨语言召回。** 中文用户问「生命周期」，英文文档写
`lifetime`；「闭包捕获」→ `closure capture`；「可变借用」→ `mutable borrow`。
这些查询 BM25 完全失效，向量确实强。这是一个可测量、可用小样本验证收益的
理由，比「向量更先进」可靠得多。

形态必须是 **hybrid**（双路召回 + RRF 融合 + 重排），不是「向量替代搜索」：
`clap derive`、`Result<T, E>`、错误信息这类查询，BM25 常胜过向量。

顺序：外部搜索 → 抓正文 → BM25 → 需要时再加向量。**不要从向量开始。**

## 3. 动画 → 只做两类，且不让模型写动画代码

**结论：可行，但范围必须钉死。**

可做的两类（都有确定性状态机，状态可枚举）：

1. **数据结构操作**：链表插入、红黑树旋转、哈希碰撞、B 树分裂
2. **执行轨迹**：排序、最短路、DP 表填充

**红线：LLM 只输出状态序列数据**（`[{step, array, highlight}]`），
由前端预置渲染器按帧播放。绝不让它写动画代码——数据错了看得见，
代码错了直接崩，而崩溃时你分不清是渲染问题还是理解问题。

不可做：抽象概念（指针、所有权、生命周期、并发模型）。没有天然可视形式，
硬做只会产出**错误类比**，比不做更有害。

判据：动画只在「执行过程不可见」时有用——治「不知道中间发生了什么」，
治不了「不知道什么时候该用」。后者要案例与反例。

成本提醒：动画是章节生成之外的独立产物（扩协议字段 + 前端渲染器 + 状态序列
合法性校验），只对标注了「过程不可见」的章做，不要全站铺。

便宜的中间态优先：**Mermaid 分步高亮 + ASCII 状态序列**（前端逐个显示），
成本近零，覆盖大部分场景。

## 4. 音频 → 明确不做

TTS 不改善文本质量，而长文没人听。唯一有价值的形态是每章 1–2 分钟的
**口播摘要**（复习场景），那是独立产物，不是正文的另一种表现形式。
