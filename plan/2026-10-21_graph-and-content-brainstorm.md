# 学习计划生成：图结构、节点职责与内容形态的深度讨论

> 日期：2026-10-21　基线：`dev/v0.1.1` @ `b50f00b`
> 参与者：教育专家（E）、博客撰写专家（W）、普通学习者（L）、资源整理专家（R）
> 形式：五轮讨论 + 交叉质疑 + 缺陷论证 + 决议。**所有判断以仓库真实代码为准**，凡涉及"现状"均给文件位置。

## 0 基线：今天的实现到底是什么

### 0.1 拓扑

```
clarify ──(有澄清问题)──> END
   │
   └─(信息完整)─> outline ─┬─ Send × 每章 ──> expand_chapter ──┐
                           └─ Send × 每阶段 ─> expand_phase_wrap ─┤
                                                                 ├─> assemble
                                                                 │      │
                                              ┌──────────────────┘      │
                                              │ 未修订                  │ 已修订（最多一次）
                                              ▼                         ▼
                                           review ──(有待回炉)──> expand_revision ──> assemble
                                              │
                                              └─(无)──> END
```

节点共 7 个（`app/graph.py:100-150`）：`clarify` / `outline` / `expand_chapter` / `expand_phase_wrap` / `assemble` / `review` / `expand_revision`。

### 0.2 节点职责与成本

| 节点 | 职责 | 输入 | 输出（state 键） | LLM 调用 | 失败行为 |
|---|---|---|---|---|---|
| `clarify` | 4 条硬完整性规则 + LLM 追问 | request | `clarifications` | 0-1 | 降级为内置文案（`nodes.py:220`） |
| `outline` | 骨架：阶段/周区间/章节标题/项目一句话/资源 | request | `outline` | 1 | 抛错（整条计划失败） |
| `expand_chapter` | 单章正文（`contentMd`） | 大纲 + 章索引 + 兄弟标题 | `chapter_drafts["p:c"]` | **N 章** | 局部化，交给回炉（`nodes.py:542`） |
| `expand_phase_wrap` | 阶段轻装 practice/assignments/project | 大纲 + 阶段 | `phase_extras["p"]` | **P 阶段** | 局部化，assemble 当场补一次 |
| `assemble` | 重组 + 程序化校验 + 标失败章 | 全部草稿 | `plan` / `validation_issues` / `failed_chapter_keys` | 0（可能补 1 次 extras） | 不阻断 |
| `review` | LLM 评审 + 分维度打分 | **全量 plan JSON** | `passed` / `review_notes` / `suggestions` / `pending_phase_indexes` | 1 | 放行（`nodes.py:855`） |
| `expand_revision` | 章级定向重扩 | 失败章键 + 评审意见 | 增量草稿 | 失败章数 | 保旧稿 + 备注 |

**成功路径预算**（无回炉）：`1 + N + P + 1` 次调用。5 阶段 / 20 章的计划 = 27 次。
**最坏路径**：再叠加一轮回炉（失败章 × 1-3 次解析重试）→ 60-100 次。

### 0.3 内容契约（当前）

- 章节形状只有三个字段：`{title, summary, contentMd}`——markdown 单一形态（`schemas.py`）。
- `contentMd`：目标 1500-3000 字，硬底线 1000 字（`validators.py:MIN_CHAPTER_CONTENT_CHARS`）。
- 强制四个固定小节：学习目标 / 前置知识 / 动手练习 / 自检清单（`validators.py:REQUIRED_CHAPTER_SECTIONS`），2026-10-21 引入。
- 每章至少一个「### 深入：××」小节，≥800 字（`chapter.yaml:29`）。
- 阶段：`objectives` + `chapters` + `practice` + `assignments` + `project`（含 steps / acceptanceCriteria）。
- 资源：**计划级** 3-6 条（`title/type/note`），**不落到章**。

### 0.4 已知故障史（后面所有缺陷论证的证据来源）

| 事件 | 根因 | 说明什么 |
|---|---|---|
| GLM `tool_call` 参数为 null，整阶段报废 | 大嵌套 schema + function calling 不可靠 | 结构化字段越多，失败面越大 |
| JSON 截断（`OutputParserException`）直接判死 | 不在重试链、未设 `max_tokens` | 单次输出越大越脆弱 |
| 阶段级重生成把 6 章全部重写 | validators 只给阶段索引 | 回炉粒度错 = 直接烧钱 |
| 计划"伪完成"（6 个空阶段标 complete） | 阶段行先建、以"有阶段行"判完成 | 状态语义未与内容绑定 |
| 真实用户问"章节怎么没有" | 错误页不显示已入库的部分数据 | 失败可见性设计缺陷 |

## 1 第一轮：四方初诊（各自最痛的三件事）

### E（教育专家）

**E1｜没有前置依赖，只有"难度递进"的口号。**
`outline.yaml` 要求"前一章是后一章的地基"，但这只是一句正确的话，没有任何可检查的产物。学习者中途卡住时，系统无法回答"我该回去补哪一章"，因为依赖关系从来没被表达出来。

**E2｜没有评估先行，整条链路是"先写内容再想怎么验收"。**
教学目标（objectives）是阶段级的 2-4 条，章节级只有"学习目标"这种自由文本，且没有任何**可判定的**检查题。结果是学员读完不知道自己是否达标，系统也不知道，只能靠字数（≥1000）判断"这章算完成了"——这是把篇幅当成学习效果的代理指标。

**E3｜没有复习机制。** 一次性生成 20 章，学完就沉底。间隔复习（spaced repetition）是教育科学里效应量最稳定的干预之一，而这里连"哪些概念值得复习"都没记录。

### W（博客撰写专家）

**W1｜每章长得一模一样，读者会在第 3 章失去兴趣。**
四个固定小节 + 固定的「深入：××」，20 章就是 20 份同构文档。同构的好处是可预测，坏处是**没有强弱的节奏**：读者不知道哪章是重点、哪章可以快读。

**W2｜没有钩子，开头全是"本章围绕 XX 展开"。**
真实产物就是这句模板（`mock.py` 里可见同一句式）。技术写作的第一段决定读者是否继续，而这里的首段信息量约等于标题的复述。

**W3｜代码示例的可信度是空的。**
正文里的代码块没有任何验证，也没有"预期输出"。读者复制粘贴跑不通时，不会怀疑是自己的问题还是文档的问题——这是技术文档最致命的信任崩塌点。

### L（普通学习者）

**L1｜打开计划，看到 5 个阶段 20 章，第一反应是"我学不完"。**
没有"今天学什么"，没有"从这里开始"。日历页有排期，详情页没有入口，两边是断的。

**L2｜读到一半退出，回来不知道自己在哪。**
章内目录（10-21 新加）解决了"章内跳转"，但跨章没有"读到哪了"的标记。计划级只有生成状态（generating/complete/failed），没有学习状态。

**L3｜某章失败了，我只看到一个红叉，不知道会不会影响其他章，也不知道点了"重新生成"要等多久。**
失败虽然可见了，但**后果与代价**不可见。

### R（资源整理专家）

**R1｜`resources` 是装饰品。**
3-6 条计划级资源，挂在最后，和任何一章都无关。读者读到第 7 章想深入某个主题时，没有任何针对性入口。

**R2｜资源没有可信度分级，也没有可达性校验。**
提示词只说"只推荐真实存在、广为人知的资源"，但 LLM 无法验证，产物也不带任何"这条我没把握"的信号。

**R3｜没有检索策略。**
"遇到不懂的怎么查"比"给你 5 本书"更有用。当前产物完全没有这一层。

## 2 第二轮：交叉质疑（对每条提议的反问与让步）

### 交锋 1：E1（依赖图）vs W（可读性）vs L（认知负担）

**W 反问 E**：你要的依赖图，读者会看吗？我在文章里加过"前置知识：本系列第 3 篇"，读者反馈是"我又不会跳着读"。
**L 附议 W**：我从来不看依赖图。我卡住了会直接往前翻，或者去搜。

**E 让步但要害不松**：读者不看图，不等于依赖关系没用。它的真实用途不是"给读者看"，而是三条：
1. **生成时防重复**——没有依赖声明，第 5 章会把第 3 章的内容再讲一遍；
2. **回炉时定范围**——某章重写后，依赖它的章节需要知道"上游变了"；
3. **答疑时定位**——"这个术语在哪讲过"能直接答。

**结论**：依赖关系的价值在**系统内部**，不在 UI。所以不需要一个"依赖图节点"，而是需要**把依赖信息作为已支付调用的一部分顺手产出**。

### 交锋 2：E2（评估先行）vs 成本

**W**：如果每章都要出题，"评估"会变成第二个内容生产环节，成本翻倍，而且 LLM 出的题自己对不对？
**E**：题的质量确实无法保证，但"没有题"是 100% 无法评估；"有题但需自行判断"至少给了锚点。而且题目**不需要新节点**——它可以是 `contentMd` 里的一个小节（`### 自测`），和正文同一次调用产出。

**L 插话**：我要的不是考试，是"我读完了能不能确认自己会了"。折叠答案的 3 道自测题，比现在这四条"自检清单"（"能不看资料复述主线"这种空话）有用得多。

**裁决**：采纳"自测题"（同调用产出，零额外成本），但**不采纳**独立评估节点。当前"自检清单"措辞空洞，就是因为它是"要求自己判断"而非"给一个可验证的问题"。

### 交锋 3：W2（钩子）vs E（内容预算）

**E 反对**：1500-3000 字里再挤 200 字钩子，硬内容就要缩水。学习者要的是知识密度，不是文采。
**W 让步并换靶子**：那我不要"钩子"，我要**信息密度**。现在首段是"本章围绕 X 展开，结合 Y 的目标场景梳理主线内容"——这句话删掉，读者零损失，省下的字给实质内容。**问题不是缺少钩子，是开头被模板句式浪费了。**

**裁决**：不要求文学性开头；要求"首段必须给出本章要解决的具体问题"（可校验：首段不得包含"本章围绕"句式）。这是**删模板**而不是**加润色**。

### 交锋 4：R1（资源落章）vs 上下文成本

**R**：资源应该按章给，读第 7 章时想看什么就有什么。
**E 反对**：每章配资源意味着每章多一次检索/匹配判断；而 `outline` 时章节标题已存在，**把资源归属作为 outline 输出的一个字段**（`resources[].forChapter`）即可，零额外调用。
**R 让步**：只要归属准确就行，不要求章级专项检索。但我要求标注**这条资源我没把握**——否则等于用假权威骗人。

**裁决**：资源在 `outline` 同调用产出，带 `phase`/`chapterTitle` 归属 + `confidence`（或 `note` 里明示"未核实"）。不加节点。

### 交锋 5：L1（今天学什么）vs 架构边界

**L**：我只要一个按钮"今天学什么"。
**W**：这只是前端入口问题，为什么要放到图结构讨论里？
**E**：因为"今天学什么"的答案依赖**学习状态**（哪些章已打卡），而当前 `Chapter` 只有生成状态（complete/failed），没有学习状态。要回答"下一步学什么"，先要知道"我学到哪了"。

**裁决**：这不是图结构问题，是**数据契约问题**——`Chapter` 需要只读的 `done` 字段（后端 join 日程），详情页才能有"继续学习"。属于独立轮次，不进本轮图改动。

## 3 第三轮：结构层——该不该加层级、该不该加节点

逐个候选，按"提议 / 反方 / 成本 / 结论"给判断。

### 候选 1：知识点依赖图节点（knowledge DAG）

**提议**：新增 `extract_knowledge` 节点，扫描全部章节正文抽取概念与依赖，产出 DAG 供 review 与回炉使用。
**反方（成本派）**：这是全量再读一遍所有正文（20 章 × 3000 字 = 6 万字上下文），一次调用极可能超限；且它读到的是**已经写完的内容**，发现问题时内容已经生成，回炉成本最高。
**反方（时机派）**：依赖信息在 `outline` 阶段就有 80% 可用——章节标题本身就隐含依赖（"变量与类型"必然先于"函数"）。等正文写完再抽，是把信息从最有用的时刻挪到最没用的时刻。

**结论：不做独立节点。** 改为在 `outline` 的每章里增加 `knowledgePoints: string[]`（2-4 个概念名），随骨架一起产出。
- 成本：0 额外调用（outline 输出多几十个 token）。
- 收益：review 可比对"章节标题 vs 知识点"，检测跨阶段重复；回炉时知道该章要覆盖哪些概念。
- 风险：outline 输出变大可能增加截断概率 → 需要在 `outline.yaml` 里明确"知识点名 ≤ 8 字，2-4 个"，并加 validators 兜底（缺失不判失败，只告警）。

### 候选 2：评估节点（自测题生成）

**提议**：独立节点为每章生成 3-5 道题 + 答案。
**反方**：N 章就是 N 次额外调用（成本 +100%），且题目与正文的**一致性**无法自动保证（题目可能考正文没讲的东西）。
**替代**：在 `chapter.yaml` 的内容要求里增加固定小节「### 自测」（3 道题 + 折叠答案），与正文同一次调用产出。
- 成本：0 额外调用。
- 收益：可判定性从"自检清单的空话"提升到"有明确问题与答案"。
- 校验：validators 检查该小节存在 + 至少包含 3 个 `?` 或 `？`（弱校验，防跑飞）。

**结论：不新增节点，纳入固定小节。**

### 候选 3：资源匹配节点

**提议**：独立节点为每章检索/匹配资源。
**反方**：没有真实检索能力（LLM 只能凭记忆），"匹配"等于再编一次；而且章节标题在 outline 时已知。
**替代**：`outline` 的 `resources[]` 增加 `phase`（或 `chapterTitle`）+ `note` 里标注把握程度。

**结论：不新增节点。**

### 候选 4：汇总/收尾节点（术语表、学习路线图）

**提议**：新增节点，汇总全书术语表 + 一页路线图。
**反方**：术语表可以完全由已有数据程序化拼接（各章 `knowledgePoints`），不需要 LLM；路线图 = outline 的阶段/章标题，也不需要 LLM。**能用确定性代码做的，不要用 LLM 做**——这是本项目最贵的一条教训（伪完成、字数当质量，都是让模型做它不擅长的事）。

**结论：不新增节点，assemble 里用纯代码生成 `glossary`（从 outline 的 knowledgePoints 去重）与 `roadmap`（阶段/章标题）。** 前端渲染即可。

### 候选 5：二级大纲（学期 → 单元 → 章）

**提议**：现在只有"阶段 → 章"，长计划（12 周以上）应该多一层"单元"。
**反方（数据派）**：`weekRange` 已经给了时间维度的层次；再加顶层会让 outline 输出翻倍，而 outline 是所有生成里**最不能失败**的一环（它失败=整条计划失败）。
**反方（体验派）**：前端已经有阶段折叠 + 章内目录，三层导航在桌面端会变成"折叠里的折叠"。

**结论：暂不做（YAGNI）。** 触发条件：出现"单阶段超过 8 章"的真实计划——那时阶段本身就太粗，应该让 outline 拆成更多阶段，而不是加层级。

### 候选 6：评审拆分（章级轻评审 + 全局结构评审）

**提议**：当前 `review` 把**全量 plan JSON**（含所有 contentMd）喂给 LLM，20 章 = 6 万字，很可能超上下文或被注意力稀释。改成：每章一次轻评审（只看这一章）+ 一次全局结构评审。
**反方（成本派）**：N+1 次调用，成本翻倍，而评审恰恰是最不值得花 N 次的地方（它不产出内容）。
**反方（有效性派）**：章级评审看到的上下文太窄，无法判断"这章与相邻章的重复"。

**折中方案（推荐）**：**缩小 review 的输入**，而不是增加调用次数。
- 输入从"全量 contentMd"改为"每章 200 字摘要 + `knowledgePoints` + validators 的问题清单 + 章节结构"；
- 正文质量的可程序化部分（字数、固定小节、mermaid 合法性、代码块数量）交给 validators；
- review 只负责**它擅长的**：跨章重复、难度递进、与目标的契合度、练习与正文的对齐。

**结论：改为缩小输入（不是加节点）。** 成本 0，还能显著降低超限风险。

### 候选 7：学习闭环节点（今天学什么）

**结论：不是生成图的问题**，是数据契约 + 前端入口的问题（见交锋 5）。独立轮次。

### 一轮小结：结构层的核心原则

> **能在已有调用里多要一个字段，就不要新加一个节点。**
> 新增节点的成本不是一次 LLM 调用，而是：+1 个失败面、+1 段上下文、+1 处状态契约、+1 个回炉时需要保持一致的东西。本项目已经有 7 个节点、14 个 state 键，再膨胀就是维护地狱。

## 4 第四轮：内容层——生成什么才叫"系统完整地学会"

### 4.1 当前内容契约的三个真实缺陷

**缺陷 A：把"字数"当成学习效果的代理指标**

- 现象：`MIN_CHAPTER_CONTENT_CHARS = 1000`，且 validator 用 `len(content)` 判断。
- 为什么是缺陷：字数与"讲清楚了"没有因果关系。一个 1200 字的空洞章节能通过校验，一个 950 字但密度极高的章节会被判失败并触发回炉——**校验在奖励注水**。
- 证据：真实 GLM 产物"673 字通过旧 500 字门限"（历史记录），说明门限只是截断下限，从未衡量质量。
- 改法：字数下限保留（防敷衍），但**同时**要求结构信号：固定小节齐全、代码块 ≥1、mermaid ≥1、「深入」小节 ≥600 字、首段不得是模板句。多信号正交，比单点阈值可靠。

**缺陷 B：「深入：××」是唯一的质量要求，但它不可验证**

- 现象：`chapter.yaml` 要求"≥800 字，覆盖机制/设计原因/误区/实例至少三个维度"。
- 为什么是缺陷：其中"至少三个维度"只能靠 LLM 自证，validator 无法检查。**不可验证的要求 = 不可依赖的要求**——模型可以写 800 字抱怨天气，形式上完全合规。
- 改法：把"维度"变成**可检测的子标题**：要求 `深入` 小节内至少 3 个 `####` 子标题（机制如何运转 / 为什么这样设计 / 常见误区 / 实例走读），validator 数子标题数量。仍是弱校验，但比"你自觉覆盖"强得多。

**缺陷 C：固定小节刚落地，就有"模板化"风险**

- 现象：四个固定小节 + 明确的句式要求。
- 为什么是缺陷：约束越硬，20 章的相似度越高；读者从第 3 章开始跳过"学习目标/前置知识"，因为它们每章一个样。
- 这不是反对固定小节——**它是可校验性的基础**，必须留。问题在于**没有强弱节奏**。
- 改法：增加一个"章型"字段（`kind: "concept" | "practice" | "project" | "review"`），由 outline 指定；不同类型允许不同的小节组合（如 `practice` 章允许省略"深入"而强调"动手练习"）。既保留可校验锚点，又打破同构。

### 4.2 内容层结论（按优先级）

| 优先级 | 改动 | 理由 |
|---|---|---|
| P0 | 首段禁模板句（"本章围绕…展开"） | 零成本，直接提升信息密度 |
| P0 | 「自测」小节（3 题 + 折叠答案）替换空洞的"自检清单" | 可判定性从 0 到有；同调用产出 |
| P1 | 「深入」小节要求 ≥3 个 `####` 子标题（可校验） | 把不可验证要求变成弱可验证 |
| P1 | 章型 `kind` 字段（outline 产出） | 打破 20 章同构，允许 practice 章不同结构 |
| P2 | 代码块要求"预期输出"注释 | 缓解"复制跑不通"的信任崩塌 |
| P2 | glossary/roadmap 由 assemble 纯代码生成 | 零 LLM 成本的结构性产物 |

### 4.3 明确不做

- **不要求"文学性开头"**：学习资料的读者要的是信息密度，钩子是博客 KPI 不是学习 KPI。
- **不给每章都配"延伸阅读"**：资源质量无法验证，20 章 × 3 条 = 60 条未核实推荐，等于批量制造虚假权威。
- **不引入数学公式/图表 DSL**：当前受众与主题（编程/工具类）不需要，增加渲染与校验成本。

## 5 第五轮：文档形态——怎么变得更好

### 5.1 已做对的

- **markdown 单一形态**（`{title, summary, contentMd}`）：这是历史上用血换来的决定——结构化字段越多，GLM 的 function calling 失败率越高（见 0.4 故障史）。正文保持 markdown，交互所需的结构信息靠**独立的小字段**承载，而不是把正文拆成字段树。
- **章内目录**（10-21）：按索引滚动，没有 slug 冲突问题。

### 5.2 还差的（按投入产出排序）

| 项 | 价值 | 成本 | 判断 |
|---|---|---|---|
| 代码高亮 | 中高——技术内容可读性核心 | 需引入 `highlight.js`（~100KB，懒加载），或改 CSS 等宽 + 行号（0 依赖） | **先做 0 依赖的排版增强**（行号、语言角标、复制按钮） |
| 打印/导出（学习手册） | 中——用户会想带走 | 前端 `window.print()` + print CSS，0 依赖 | 值得做，一次成型 |
| 术语锚点（点术语看释义） | 中——但依赖 glossary 与正文标记 | glossary 可由 knowledgePoints 生成；正文标记需 LLM 配合 | P2，先有 glossary 再谈锚点 |
| 笔记联动（已有占位页） | 高——学习闭环核心 | 需要笔记与章的关联存储 | 独立轮次 |
| 章节标题可复制/深链 | 低 | — | 不做 |

### 5.3 一条设计红线

> **正文永远是 markdown 字符串，不允许把正文内容拆成结构化字段。**
> 唯一例外是"需要被程序读取的判断依据"（`knowledgePoints`、`kind`、`resources`），它们必须**短**、**可校验**、**不承载正文**。

## 7 决议与路线

### 7.1 一句话结论

> **不要再加节点，也不要加层级。当前图结构（7 节点 / 章级扇出 / 一次回炉）是对的骨架。真正的收益在"让已有调用多产出可校验的结构信息"，以及"把评审输入从全文换成摘要"。**

### 7.2 落地顺序（每步独立可验证）

**第一批（0 额外 LLM 调用，纯契约增强）**
1. `PhaseOutline` 增 `chapterKnowledges`（章标题 → 知识点 2-4 个）与 `kind`（章型）——三端协议 + prompts + validators
2. `chapter.yaml`：禁模板首段、加「自测」小节、`kind` 差异化小节组合
3. `review.yaml` + `review_node`：输入改为摘要 + knowledgePoints + 校验问题
4. `assemble`：纯代码生成 `glossary` + `roadmap`
5. validators：`深入` 子标题数量、代码块预期输出、`自测` 小节存在性

**第二批（前端，0 后端改动）**
6. 代码块排版增强（行号 / 语言角标 / 复制按钮）
7. 打印样式与导出
8. glossary / roadmap 渲染

**第三批（独立轮次，需三端协议 + DB）**
9. 详情页「今天学什么 / 继续学习」+ 打卡态（`Chapter.done`）
10. 笔记与章关联
11. 间隔复习（依赖 knowledgePoints 落库）

### 7.3 明确不做（本轮）

- 知识点抽取节点、评估节点、资源匹配节点
- 二级大纲（单元层）
- 章级并行评审（N+1 次调用）
- 第二次回炉（当前 `revised` 单次上限是对的：回炉失败率高于收益）

---

## 8 需要人决策的四个点

1. **`kind` 章型是否值得**：它打破同构，但也让 validators 与提示词复杂化（不同类型不同校验）。收益是体验，成本是维护。
2. **review 缩输入后，正文质量谁负责**：目前只有 validators 的弱校验（字数、小节、mermaid）。是否接受"正文质量不做 LLM 全局评审"？
3. **resources 的"未核实"如何表达**：`confidence: high|medium|low` 字段，还是只在 `note` 里写"（未核实）"？前者可筛选，后者更自然。
4. **glossary 是否需要人工可编辑**：纯代码生成意味着术语表永远等于 outline 的知识点；若要允许用户补录，就变成数据资产（需存储）。

## 9 反对意见存档（未采纳的理由）

| 提议 | 提出者 | 未采纳原因 |
|---|---|---|
| 每章单独评审 | E | +N 次调用，且章级上下文看不到跨章重复 |
| 文学化开头 | W | 与学习资料的读者预期相反，且挤占内容预算 |
| 章级资源检索 | R | 无真实检索能力，凭记忆"匹配"等于二次编造 |
| 依赖图可视化 | L（转述 E） | 读者不看，价值在系统内部而非 UI |
| 二级大纲 | E | outline 输出膨胀风险 > 层次收益；触发条件未出现 |
| 取消固定小节 | W | 它是目前唯一可程序化验证的质量锚点 |
